## STRATEGIES_AND_HARD_RULES
[shr-00056] helpful=134 harmful=1 :: When retrieving authentication credentials (username, password) for any API, ALWAYS use the `apis.supervisor` object (e.g., `show_profile`, `show_account_passwords`) as the authoritative source. Never manually parse lists, guess account names, or hardcode credentials, as this leads to brittle code and potential security issues.
[shr-00070] helpful=103 harmful=0 :: After calling any authentication API (e.g., `login`), immediately extract the credential (e.g., `access_token`) from the return value and assign it to a dedicated variable. Do not use this variable in subsequent API calls until it has been explicitly defined and verified, even if the variable name seems obvious. This prevents `NameError` exceptions caused by undefined variables in loops or conditional blocks.
[shr-00088] helpful=92 harmful=0 :: When interacting with the supervisor or completing a task, NEVER hardcode identity information (e.g., email addresses, usernames) or task status values. Always retrieve the supervisor's profile using `apis.supervisor.show_profile()` to get the current email dynamically, and explicitly pass `status='success'` to `apis.supervisor.complete_task()` to ensure the task is formally marked as completed according to the API contract.
[shr-00011] helpful=80 harmful=3 :: When fetching paginated lists (e.g., playlists, transactions) to find an item meeting a specific condition (e.g., duration >= workout time), do not assume a single call with a high `page_limit` is sufficient. Always implement a loop that iterates through pages until either a matching item is found or no more pages are returned, to avoid missing valid candidates in subsequent pages.
[shr-00078] helpful=61 harmful=1 :: When paginating through APIs to retrieve a complete list of entities, never assume a fixed page count or a specific 'has_more' flag. Always implement a robust loop that continues fetching pages until the API returns an empty list (or a list with fewer items than the page limit, indicating the final page), ensuring no data is missed at the end of the dataset.
[shr-00020] helpful=42 harmful=0 :: When calling authentication APIs (e.g., `login`), never assume the function returns the credential directly. Always inspect the return value to determine if the token is nested inside a dictionary (e.g., `result['access_token']`) or returned as a raw string.
[shr-00074] helpful=42 harmful=0 :: When searching for contacts using APIs like `search_contacts` (e.g., filtering by 'coworker' or 'friend'), never assume a single call returns the complete list. These APIs often have a default page limit (e.g., 10) and require explicit pagination. Always implement a loop iterating through `page_index` (e.g., 0 to 9) to collect all contacts into a single list or set before proceeding to cross-reference them with other data sources.
[shr-00001] helpful=38 harmful=0 :: For any API call that modifies state (e.g., like, delete, update), explicitly verify that the `access_token` or authentication credentials are included in the function arguments. A 401 Unauthorized error on a write operation almost always indicates a missing or expired token, not a logic error in the data filtering.
[shr-00019] helpful=35 harmful=1 :: When aggregating data from multiple sources (e.g., library vs. playlists), never assume all returned objects use the same key names for unique identifiers. Always inspect the actual keys in the returned objects (e.g., `id` vs `song_id`) and normalize them to a consistent key before performing set operations or deduplication.
[shr-00005] helpful=32 harmful=0 :: When cross-referencing entities (e.g., contacts vs. transactions) retrieved from different APIs, always use unique system identifiers (like 'email', 'id', or 'uuid') for matching. Never rely on human-readable fields (like 'name', 'display_name') for exact matching, as these may contain variations, duplicates, or formatting differences that lead to false negatives or positives.
[shr-00008] helpful=32 harmful=0 :: When calling authentication APIs for specific apps (e.g., Phone, Venmo), never assume the parameter name for credentials is intuitive (e.g., 'phone_number'). Always inspect the API documentation or the result of `show_api_descriptions` to confirm the exact parameter name (e.g., 'username' vs 'phone_number') before passing values.
[shr-00071] helpful=23 harmful=0 :: When performing state modifications on a list of entities (e.g., updating multiple alarms), adopt the 'fetch-all-process-all' pattern: retrieve the entire list once, filter/identify targets in memory, and then perform updates. Avoid the 'fetch-one-update-one' pattern unless necessary, as it increases API latency and the risk of state management errors.
[shr-00031] helpful=24 harmful=2 :: Before implementing complex search logic (e.g., cross-referencing contacts, paginating through lists), always inspect the initial API response to see if the target entity is directly present. If the required data (e.g., transaction details, user info) is available in the first page or unpaginated result, filter directly using that data instead of assuming a multi-step lookup is required.
[shr-00082] helpful=19 harmful=1 :: When determining time-based thresholds (e.g., 'this year', 'last year', 'last 30 days'), NEVER hardcode specific years or dates. Always calculate the threshold dynamically using the `DateTime` class (e.g., `DateTime.now().start_of('year').subtract(years=1)`) to ensure the logic adapts to the current execution time and remains valid across different test environments.
[shr-00027] helpful=18 harmful=0 :: When iterating through a list of items (e.g., songs in a library) and needing to fetch details for each, never assume the unique identifier key in the list object (e.g., 'id') is the same as the key expected by the detail API (e.g., 'song_id'). Always inspect the list response schema first to extract the correct ID key before calling the detail API.
[shr-00053] helpful=18 harmful=0 :: When filtering transactions or logs against a list of contacts (e.g., roommates), if the contact list provides a unique identifier field (like 'email'), rely EXCLUSIVELY on that field for matching. Do not add secondary checks using human-readable fields (like 'name', 'first_name', 'last_name') unless the unique identifier is explicitly missing, as names are prone to formatting variations, duplicates, and false positives.
[shr-00022] helpful=17 harmful=0 :: When filtering transactions or logs by a relative time (e.g., 'yesterday', 'last week'), never hardcode a specific date string (e.g., '2023-05-19'). Always calculate the target date dynamically using the current system time to ensure the query matches the actual execution context.
[shr-00085] helpful=15 harmful=0 :: When calling the `show_song` API (or similar detail endpoints for media entities like `show_album`), never assume it requires an `access_token` just because the parent list API (e.g., `show_song_library`) did. Inspect the specific API documentation or attempt the call without auth first; these endpoints are often public and passing an auth token is unnecessary or may cause errors if the parameter is not expected.
[shr-00148] helpful=15 harmful=0 :: When performing state modifications (e.g., updating or creating reviews, likes, follows) on Spotify, always explicitly pass the 'access_token' obtained from the login step. Unlike list-view or detail-view endpoints which are often public or use session-based auth, action endpoints frequently enforce strict authentication. Do not assume that a successful login earlier in the script automatically grants access to these specific endpoints without passing the token.
[shr-00077] helpful=14 harmful=0 :: When extracting unique identifiers from a nested data structure (e.g., a list of songs where each song contains a list of artists), never assume the ID is at the top level of the list item. Always implement a nested loop or list comprehension to traverse the inner list (e.g., `song['artists']`) and collect the specific ID field (e.g., `artist['id']`) into a set before performing any filtering or matching operations.
